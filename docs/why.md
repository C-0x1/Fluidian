## The problem

Adding intelligence to an interface today usually means building, for every feature, the same stack of things by hand:

1. a prompt, and the code that fills it;
2. a schema for the answer, and a parser that survives the model ignoring it;
3. a place in the interface to show the result, a loading state, an error state and a way to undo it;
4. a decision about what the model may see, and code that removes what it may not;
5. protection against instructions hidden in the data the model reads;
6. a cache, a budget and a fallback for when the provider is slow or down;
7. a record of what was generated, by which model, from what input.

Each team writes these again for each feature, each slightly differently. The second language on the team writes them a third time. The result is interfaces where "AI" is a chat box in the corner, because that is the only surface anyone had time to build properly.

A second problem sits beside it. Interface code is tied to one language and one platform. The team that owns the data writes Go or Rust or PHP; the interface is written again in TypeScript, behind an API invented to connect them; the mobile version is written a third time.

## The idea

Fluidian makes two decisions and follows them all the way through.

**Intelligence is part of the component model.** A capability attaches to a component the way an event handler does: `.ai("data.query")`. The capability is a typed contract declared once in the engine. The runtime knows how to present its result on that kind of component. The kernel applies the same safeguards to every call. Nothing is written per feature.

**The interface is data.** An application returns a scene: a tree of nodes described as JSON. Any language can produce JSON, so any language can describe an interface. Any platform that can run the runtime can show it. Because scenes are data, they can be validated, repaired, generated by a model, converted between languages and compared for equality.

Everything else in the framework is a consequence of those two decisions.

## Seven things it removes

| You no longer write | Because |
| --- | --- |
| **Prompts and parsers** | Each of the 185 capabilities carries its instruction and its input and output schema. Model output is requested as strict structured output, validated, and repaired once if it fails. |
| **Result surfaces** | Sixteen presenters cover how a result reaches the screen: ghost text, a reviewable diff, chips, an insight panel, a filled form, a composed region, a popover, a command, a chat reply, an audit list, a theme, media. Loading, failure and undo come with them. |
| **Safeguards** | Redaction of personal data, an injection shield, moderation, consent scopes, per-session budgets and policy lists run on every call, in a fixed order, in one place. |
| **A fallback** | Every capability has a deterministic local implementation. With no key, or when the provider fails, the same call is answered locally and marked as such. |
| **A separate front end** | The service that owns the data describes its own interface, in its own language. There is no second codebase and no API between them. |
| **A mobile rewrite** | The same scene takes the iOS or Android skin, installs from the browser and wraps into a native shell. |
| **A port** | `fluidian convert` rewrites an application into any of the other thirteen languages and verifies the result against the original. |

## What is new here

Individual pieces of this exist elsewhere. These are the parts that, as far as we know, do not come together anywhere else.

### Capabilities as a registry, not a library of helpers

A capability is data: an id, a schema in and out, an instruction, a tier, an offline implementation, a presenter and a consent scope. Because it is data, the same registry generates the SDK surface for fourteen languages, the reference documentation with real example output, the strict JSON schemas sent to the model, and the contract tests that hold every capability to its declared shape. Adding a capability is adding one declaration.

### An offline twin for every capability

The Reflex engine implements all 185 capabilities deterministically: date and quantity parsing, format repair, table querying, anomaly detection, forecasting, chart selection, layout composition from intent, colour and contrast mathematics, summarisation by extraction, accessibility audits and more. It is not a mock. It is what runs the gallery, the showcase, every screenshot in this repository and the whole test suite, and it is what your users get when a provider has an outage.

### Generated interfaces that cannot leave the design system

When a model composes an interface, it returns a scene. The engine normalises that scene against the component registry before it is shown: unknown components, props, actions and capabilities are removed, types are coerced, ids are made unique, contrast is repaired. A generated region carries provenance and a refine bar. A model can arrange your components; it cannot invent markup, styles or behaviour.

### Behaviour as data

Portable logic puts client behaviour inside the scene: state, bindings, conditional and repeated content, and actions written as short strings that a small interpreter runs. It needs no handler, so it is instant; it is identical in every SDK, so it converts between languages with nothing to port; and it is interpreted without `eval`, so it is safe to accept from a model. See [Portable logic](portable-logic.md).

### Conversion that is proved, not promised

Translating source code between languages is unreliable, and the usual answer is to hope. Fluidian's converter works on what an application serves instead of on its text, and it finishes by building the result, running it and comparing every scene with the original. A conversion is reported as verified only when they are identical. The same gate applies to model-written translations of handler code: a translation that does not reproduce the source is rejected and the verified version is kept. See [Converting between languages](convert.md).

### Design decisions checked by arithmetic

Themes are generated in the OKLCH colour space and every text and surface pair is measured against WCAG contrast targets; pairs that fail are adjusted by the smallest perceptual step that passes. This applies to the twenty-seven presets, to a theme described in a sentence, and to colours a model proposes. An unreadable theme cannot be applied.

### A model line-up that can change under you

Model names are configuration. Each tier has a preference list; the engine asks the account which models it can use, takes the first that exists, and negotiates request parameters with the provider when one is rejected. A model being retired is a log line, not an outage.

## What a feature costs to build

A table people can question in plain language, as an example.

| Step | By hand | With Fluidian |
| --- | --- | --- |
| Describe the columns to the model | Write and maintain a prompt | Derived from the rows |
| Get a structured query back | Design a schema, parse, retry | Declared in `data.query` |
| Apply it | Write a filter and sort engine | In the kernel |
| Show it | An input, a spinner, chips for the active filter, a clear button | The table's presenter |
| Keep customer names out of the request | Write redaction | Kernel stage 4 |
| Survive a hostile cell value | Write injection defence | Kernel stage 5 |
| Work when the provider is down | Write a second implementation | Reflex |
| Know what happened later | Add logging | Provenance and the ledger |
| Do it again in the Go service | Repeat all of the above | The same one line |
| **Code you write** | **Several hundred lines, per language** | **`.ai("data.query")`** |

## Check it yourself

Every claim above can be checked on your own machine, offline, in a few minutes.

| Claim | Command |
| --- | --- |
| It runs with no key and no network | `./fluidian gallery --offline` |
| 185 capabilities exist and answer | `./fluidian features` and `./fluidian ai data.query` |
| Each capability meets its contract | `./fluidian test --quick` |
| Fourteen SDKs agree message for message | `./fluidian test` |
| An application converts and verifies | `./fluidian convert examples/portable/app.py --to all --probe` |
| A conversion that differs is caught | `cd tests/engine && python3 -m unittest test_convert -k differs` |
| Generated scenes are grounded | Open **Trust** in the gallery and read the repair list |
| Personal data is redacted | `./fluidian ai trust.redact --input '{"text":"Call Dana on +1 415 555 0134"}'` |
| Themes pass contrast | `./fluidian ai design.theme_prompt --input '{"prompt":"neon on black"}'` |
| It behaves the same on a phone | Add `?platform=ios` or `?platform=android` to any address |
| Your key and models work | `./fluidian doctor --live` |

## When not to use it

A framework that claims to suit everything deserves suspicion. Fluidian is the wrong tool when:

- **You need pixel-level custom rendering**: a game, a canvas editor, a 3D scene. Fluidian composes from a component registry; it does not give you a drawing surface.
- **The application must work with no server at all.** Scenes and handlers live in your application process. Portable logic and the cached shell soften a lost connection; they do not replace the server.
- **You already have a large front end you are happy with.** Embed a Fluidian application inside it with `<fluidian-app>`, or use the kernel's capabilities through `ctx.ai`, rather than rewriting.
- **You need thousands of simultaneous sessions on one process today.** The engine is a single Python process built for clarity and for running anywhere. Scale it by running several behind a load balancer with session affinity; see [Deployment](deployment.md).
- **Hand-tuned prompts are your product.** The kernel's capabilities are general. You can add your own capability with your own instruction, but if every call is bespoke you will not gain much from the registry.
