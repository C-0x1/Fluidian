# Contributing to Fluidian

Thanks for taking the time. This page covers how the repository is organised,
how to run the checks, and what a change needs before it can be merged.

## Getting set up

```bash
git clone https://github.com/fluidian/fluidian.git
cd fluidian
./fluidian doctor        # what is installed, what is missing
./fluidian test --quick  # engine and runtime tests, a few seconds
```

The engine needs Python 3 and nothing else. Node.js 18+ is needed for the
runtime tests and static export. The language toolchains are optional; install
the ones you work on with `scripts/install-toolchains.sh go rust` (or all of
them with no arguments).

## Where things live

| Path | What it is |
| --- | --- |
| `engine/fluidian/` | HTTP engine, AI kernel, capability registry, Reflex engine, CLI |
| `runtime/` | Browser runtime: ES modules, stylesheet, design tokens, font |
| `sdks/<language>/` | One SDK per language, with a quickstart and the conformance app |
| `spec/` | Published component and capability specs, golden conformance transcript |
| `examples/gallery/` | The gallery app: one page per capability family |
| `examples/showcase/` | 85 complete screens in six groups; most screenshots are taken from it |
| `examples/portable/` | A small app used to test conversion between languages |
| `tests/` | Engine, runtime and browser tests |
| `tools/` | Code generation, documentation generation, export, screenshots |
| `docs/` | Guides and generated reference |

## The registries are the source of truth

Components are declared in `engine/fluidian/components.py` and capabilities in
`engine/fluidian/capabilities/`. SDK factories, the published specs, the
reference documentation and parts of the test suite are generated from them:

```bash
./fluidian codegen   # SDK factories, spec/*.json, golden transcript
./fluidian docs      # docs/reference/*, sdks/*/README.md
```

Never edit a file that starts with "Generated by". The test suite fails when
generated files are stale.

## Adding a capability

1. Declare it with `cap(...)` in the family module: id, title, summary, the
   reason it exists, input and output shapes, an example, and the presenter.
2. Give it a Reflex implementation so it works offline and in tests.
3. Run `./fluidian codegen && ./fluidian docs`.
4. `./fluidian ai your.capability` to try it; `./fluidian test --quick` to
   confirm the contract tests pass (every capability must answer its own
   example offline and send a strict-valid schema to the provider).

## Adding a component

1. Add the entry to the registry (props, events, example).
2. Add the renderer in `runtime/components.js` and styles in `fluidian.css`.
3. Regenerate; the conformance scene and all fourteen SDKs pick it up.

## Changing an SDK

Each SDK must reproduce `spec/conformance/golden.json` exactly:

```bash
./fluidian test --sdk rust --sdk go
```

The harness builds the SDK's conformance app, drives it through a scripted
session and reports the first message that differs.

## Before you open a pull request

- `./fluidian test` passes (SDKs you cannot build locally are skipped and
  will run in review).
- New behaviour has a test. Bug fixes come with a test that failed before.
- Public behaviour is documented, and the changelog has an entry.
- Commits explain why, not just what.

## Style

Python follows PEP 8 with a 160-column limit and type hints on public
functions. JavaScript is plain ES modules without a build step. SDK code
follows the conventions of its language and must not add dependencies.
